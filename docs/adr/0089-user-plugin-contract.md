# 0089. User plugins are declarative packages over a closed, isolated contract

Status: accepted

## Context

[ADR 0085](0085-one-plugin-model-with-separate-trust-tiers.md) gave system and user plugins one
contribution and settings model with separate trust tiers. A user plugin is code or data the user
installs, so it is untrusted: the application holds the session credentials, the vault, host
connections and the user's files in the same process. Letting a package reach any of them, or
letting host code reach them on a package's behalf, would turn a status bar widget into an
escalation path. The first runtime has to be one that cannot run code at all.

## Decision

**What a package is.** A user plugin is a function from a snapshot of what it was granted to a
view, and from an event to at most eight effects. The plugin and host exchange plain data only.
The contract is `nocterm-plugin-api` (domain layer): the capability table, `Snapshot`, `View`,
`Effects`, `Event`, `HostError`, the manifest and its validation, grants, the template language and
the ports `PluginPackages` and `PluginRuntime`. Guest text is sanitized and bounded before it is
shown. A package cannot express a built-in privilege: capability ids never equal a system
contribution or plugin id (an application test checks this against the catalog), and a view is a flat arena (`parent < index`, unique keys, depth at
most 8), so no parser recurses over guest input.

**Declarative first.** The first runtime, `DeclarativeRuntime`, interprets a manifest. A view is
literal text with `{capability.field|filter}`, `{settings.key}` and `{item.field}` holes and the
filters `round(n)` (at most 2 decimals), `percent`, `hh-mm` and `threshold(low, high)`. There is no
concatenation, repetition, regex or function, and a value is inserted as literal text and never
parsed again. Every hole is resolved against the declared capabilities and settings when the
package is read, so a mistake is a manifest error shown before consent. A declarative package
produces no effect, so it cannot request an effect capability. Effects are a closed set; a
runtime that produces them is bound by the targets the manifest declared, and the host's broker
enforces that.

**Identity and consent.** A user plugin id is `user-<publisher>-<id>`, and only such ids are valid
for packages, so a package cannot choose a path or shadow a system plugin. A grant is bound to
`(PluginId, ContentHash)`, where the hash is the SHA-256 of the exact buffer that was parsed; a
changed file asks again. `Grant::check` separates `NotGranted` from `Unavailable`. The tier
`clamp` bounds what a user plugin may place (zones, kinds, and icons from a set of generic
shapes that no system contribution uses, so an icon never stands for a built-in). User
plugins never write to `[plugins]`; `nocterm-plugin-enablement` keeps `user-` ids out of it.

**The packages adapter.** `nocterm-plugin-packages` (adapter layer) implements `PluginPackages`:
a bounded (256 KiB) no-follow read through `nocterm_core::fs::read_regular_bounded`, UTF-8 and
TOML parsing into the api DTOs behind an API version gate, the hash, private atomic publication
with `write_private_atomic`, re-hashing at load, and removal. TOML parsing lives here because the
domain crates are `no_std`.

**Naming.** Struct field names and manifest keys are `snake_case`; enum values, icon names and
capability ids are `kebab-case`.

**Isolation.** `cargo xtask architecture` runs an isolation check
([guardrails](../architecture/guardrails.md#isolation-of-the-plugin-crates)) driven by
`xtask/architecture-policy.toml`. It closes the transitive `nocterm-*` and external dependency
closure of each plugin crate (I1), makes `nocterm-plugin-model` and `nocterm-plugin-api`
`#![no_std]` with `alloc` so `fs`, `net`, `process` and `env` are unreachable (I2), forbids I/O
paths in the std-based isolated crates (I2b), closes the gpui receiver methods the view, ports and
host crates may call (I3), bans build scripts, macros, `unsafe`, `include!` and path-valued serde
attributes (I4), restricts the dependents of the provider port (I5), and asserts that the default
build of `nocterm` does not contain a user-plugin crate. These rules guard against host-side
regressions; they do not cover I/O reached through an allowlisted dependency's own API, nor a
confused deputy, which stay design-review items.

**Shipping gate.** Everything is behind the cargo feature `nocterm/user-plugins`, off by default and
compiled out of default and release builds. CI builds, lints and tests the workspace with it on.
Runtimes that execute code (a Wasm interpreter, a script engine, a helper process) are not part of
this decision and need their own ADR; they will implement the same `PluginRuntime` port. A JIT
inside the process that holds the vault is excluded.

**The API surface.** `crates/plugin-api/api-surface.json` is generated by `cargo xtask docs` from
the capability table, the limits and the template vocabulary, and `docs --check` fails when it is
stale, so a contract change is visible in review and the version in `API_VERSION` is bumped
deliberately.

## Consequences

- A malicious package can show bounded, sanitized text in the places the manifest and the clamp
  allow and ask for the effects it declared; it cannot read a file, open a connection, press a key
  or see another plugin's state.
- The domain crates `nocterm-plugin-model` and `nocterm-plugin-api` are `no_std`; their consumers
  keep using them unchanged because `alloc` is available everywhere.
- Adding a dependency to a plugin crate, a new provider crate, a gpui receiver call or an I/O path
  is a reviewed edit of the policy file with a reason.
- Declarative packages cover widgets and panels over granted values, lists and settings; logic
  needs a later runtime behind the same port.
- The package format is a TOML file whose shape is documented by the manifest rules and the
  generated surface file; a breaking change raises the API version and keeps the version gate
  readable by older hosts.
